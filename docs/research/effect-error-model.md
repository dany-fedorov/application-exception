# Effect error model: lessons for Application Exception

Checked **2026-09-10**, using official Effect documentation/source and the ECMAScript specification. This is design research; no runtime dependency or implementation is proposed.

**Version scope.** The inspected `v3` package declares **3.22.2**; `main` declares **4.0.0-rc.113**. These are observed source versions, not an audit of npm dist-tags. Branch links can change. Some official migration prose still says “beta”; prefer the actual signatures and package versions below. [v3 package](https://raw.githubusercontent.com/Effect-TS/effect/v3/packages/effect/package.json), [v4 package](https://raw.githubusercontent.com/Effect-TS/effect/main/packages/effect/package.json), [migration overview](https://github.com/Effect-TS/effect/blob/main/MIGRATION.md).

Earlier v4 betas used `Schema.TaggedErrorClass`. That constructor was renamed **back to `Schema.TaggedError`**, alongside `ErrorClass` → `Error` and the native instance schema → `ErrorInstance`. Copying a beta example into the inspected RC can therefore fail. [Rename commit](https://github.com/Effect-TS/effect/commit/592dd361645739ac0cd8e6babb084cd27403c172).

**Verified behavior: error values and control flow.** In v3, `Data.TaggedError("NotFound")<Fields>` produces a constructor accepting the declared fields, adding a literal readonly `_tag`, and setting the error name from the explicit tag. Its base ultimately extends JavaScript `Error`; instances are yieldable failures inside Effect generators. The Data constructor assigns supplied fields without schema validation. Its `toJSON` merges constructor arguments and enumerable instance fields: this is neither a privacy policy nor validation of a wire format. [Data implementation](https://github.com/Effect-TS/effect/blob/v3/packages/effect/src/Data.ts), [native Error base](https://github.com/Effect-TS/effect/blob/v3/packages/effect/src/internal/core.ts).

An `Effect<A, E, R>` tracks anticipated failures in `E`; compositions accumulate an error union. `catchTag` dispatches on `_tag` and removes a recovered alternative, while retaining unhandled errors; handlers can introduce further failures. `catchTags` provides several handlers together. The discriminator is structural: recovery does not require a particular error superclass. [Expected errors and tagged recovery](https://effect.website/docs/v3/error-management/expected-errors).

Failures and defects describe how a computation terminated, not two intrinsic categories of JavaScript error classes. `Cause.fail(error)` records a typed failure; `Cause.die(value)` records an untyped defect. Thus `E = never` does not guarantee successful execution. This distinction requires Effect's computation model, and cannot follow merely from extending native `Error`. [Cause documentation](https://effect.website/docs/v3/data-types/cause).

**Verified behavior: schemas and boundaries.** In v3, `Schema.TaggedError<Self>()(tag, fields)` combines an error class with a schema. Its constructor validates fields by default; an explicit option can disable validation. Decoding the encoded representation validates it and constructs a class instance; encoding uses the declared schema. Runtime fields and encoded fields can differ through transformations. Constructor typing, runtime validation, and transport decoding are separate guarantees. [Schema class documentation](https://effect.website/docs/v3/schema/classes), [TaggedError and class implementation](https://github.com/Effect-TS/effect/blob/v3/packages/effect/src/Schema.ts).

For v3, `Schema.decodeUnknownEither` returns `Either<A, ParseError>`; effectful `decodeUnknown` exposes the parse error in its failure channel. A schema union can validate supported tagged alternatives. JSON text also needs parsing, and its encoded values must be JSON-compatible; arbitrary `unknown` fields do not gain a safe transport representation by being inside an error. [v3 Schema API](https://github.com/Effect-TS/effect/blob/v3/packages/effect/src/Schema.ts), [basic schema usage](https://effect.website/docs/v3/schema/basic-usage).

In the inspected v4 RC, `Schema.TaggedError` remains schema-backed; `Schema.toCodecJson` derives a JSON codec, whose encoding/decoding can still fail. Parsing APIs include `decodeUnknownEffect`, `decodeUnknownExit`, and `decodeUnknownResult`; `SchemaError` carries structured issues. The source explicitly warns that reported inputs and custom messages can disclose input and are not automatically sanitized. [v4 Schema API](https://github.com/Effect-TS/effect/blob/main/packages/effect/src/Schema.ts).

**Verified behavior: outcome and causality.** V3 `Either` has `Right` success and `Left` failure; v4 `Result` uses `Success`/`Failure`, carrying `.success`/`.failure`. The respective `Effect.either`/`Effect.result` conversions capture typed failures, not every possible termination. The v4 source explicitly excludes defects and interruption. `Exit<A, E>` instead represents success or failure carrying `Cause<E>`. [v3 Either conversion](https://github.com/Effect-TS/effect/blob/v3/packages/effect/src/Effect.ts), [v4 Result](https://github.com/Effect-TS/effect/blob/main/packages/effect/src/Result.ts), [result conversion](https://github.com/Effect-TS/effect/blob/main/packages/effect/src/Effect.ts), [Exit](https://effect.website/docs/v3/data-types/exit).

V3 Cause distinguishes `Empty`, `Fail`, `Die`, `Interrupt`, `Sequential`, and `Parallel`. V4 removes the composition tree and collects `Fail`/`Die`/`Interrupt` reasons in an array; it no longer records sequential versus parallel composition. This runtime failure model is separate from native `Error.cause`. [Cause migration](https://github.com/Effect-TS/effect/blob/main/migration/cause.md).

JavaScript's standard `cause` retains a supplied value, which need not be an Error. `AggregateError` retains an iterable's values in `.errors` and can itself have a `cause`. Both properties are non-enumerable. These standards provide ordinary causal wrapping and aggregation, without fibers or an Effect Cause tree. [InstallErrorCause](https://tc39.es/ecma262/multipage/fundamental-objects.html#sec-installerrorcause), [AggregateError constructor](https://tc39.es/ecma262/multipage/fundamental-objects.html#sec-aggregate-error-constructor).

**Repository comparison.** [ApplicationException.ts](../../src/ApplicationException.ts) already extends Error, stores `details`, distinguishes display text, and tracks multiple `causes`. It calls `super(icfg.message)` without native cause options. `code` is optional and accessed through methods; subclass-derived codes are configurable. `toJSON` exports diagnostics including details, stack, causes, and raw templates. Its declared `ApplicationExceptionJson` names `compiled_message`, while the implementation emits `message`; required `stack` can be omitted for wrappers. The [README](../../README.md) already encourages returning errors as ordinary values, and [TODO](../../TODO.md) requests JSON schema options.

**Design recommendations, inferred from those findings.**

1. Add an explicit, stable literal tag and typed construction requiring the complete domain payload. Keep tag identity independent of constructor names, message wording, and numeric transport status. This supplies useful TypeScript narrowing without a computation framework.
2. Prefer constructor-time message rendering from complete details, so native `.message`, stack headings, and diagnostics agree. Specify immutability deliberately; TypeScript `readonly` does not freeze nested payloads. Keep legacy builder behavior as a separately documented compatibility surface.
3. Support native `.cause: unknown` and native aggregates. Do not infer runtime concurrency semantics from an array of underlying errors. Any migration from existing `.causes` needs an explicit compatibility rule.
4. Define separate diagnostic and public representations. Public projection should select approved fields and safe messages, with a generic unknown-error fallback. Never treat `toJSON`, schema encoding, or “expected error” classification as authorization to expose details, stack, or causes.
5. Treat incoming serialized errors as `unknown`. Validate envelope version, tag, and payload before returning a typed wire value or rehydrating a registered class. Unknown versions/tags should remain explicit decode failures or unknown remote errors. A caller-supplied decoder or optional schema adapter is sufficient; a new schema engine is unnecessary.
6. Preserve interoperability with callers' existing Result/Either/Effect choices. Returning a typed error value is useful already; reproducing typed propagation, fibers, defects, and scheduling would change this library's purpose.

Priority: establish tag/payload and native Error contracts first; reconcile diagnostic serialization next; add public projection and validated wire adapters after those contracts are stable.
